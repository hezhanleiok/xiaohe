# 2026-10-19

## 建立 git 基线（0.1.29）

用户要求：「把当前的建立基线，进行 git，同步修改根目录说明文件」。

### 做了什么

1. **`git init`**（仓库此前不存在），分支 `master`，仅本地、无远端。
   - 顺手设了 `core.quotepath=false`，中文文件名在 `git status`/`ls-files` 里正常显示。
2. **`.gitignore`** 重写，分四类并写清理由：
   - 可重建：`app/libs/*.aar`、`app/libs/engine-sources.jar`、`app/build/`、`.gradle/`、`/.tmp/`、`/engine/.tmp/`
   - 体积大：`_lan/*.apk`（7 个 × 37MB）、`dist/`（74MB）
   - 一次性：`_ctx_asst.txt`、`_ctx_user.txt`、`build-engine-classes.jar`
   - 本机：`local.properties`、`*.keystore`、`*.jks`
3. **`.gitattributes`**：`* text=auto eol=lf` + 二进制白名单。
   原因：Windows 上 `core.autocrlf` 会把源码 checkout 成 CRLF，导致每次 diff 全文件变化。
4. **首次提交** `d64fcb4`：140 文件 / 25,187 行 / 40MB，`.git` 实际 18MB（.so 压缩率高）。
5. **tag** `baseline-0.1.29`（annotated，指向 `d64fcb4`）。
6. **`基线说明.md` 同步更新**：
   - 第 1 节新增「版本基线与 git」小节：进/不进仓库的清单（带原因表）、回滚命令、
     每次改完的标准流程；
   - 第 8 节「发布流程」补第 4 步：`git add -A && git commit && git tag -a baseline-<版本>`。

### 关键判断（为什么这样切）

- **`app/src/main/jniLibs/*.so` 必须进仓库**（37MB）。`libaether.so` / `libpsiphon.so`
  是预编译第三方二进制，重建不出来；不进仓库的话 clone 之后打不出包。
- **`engine/third_party/wireguard` 必须进仓库**（466KB）。`device/awgjunk.go`（AWG junk）
  和 `device/force.go`（我们加的 ForceHandshake）都在里面，是能连上的前提。
- **`engine.aar` 不进仓库**。它是 `gomobile bind` 的产物，每次改 Go 都变；
  重建步骤写在基线说明第 1 节（含 UTF-8 与 GOTMPDIR 两个坑）。
- **APK 不进仓库**。发布包靠 `_lan/` 目录 + `_lan/index.html` 下载页；仓库里只留下载页。

### 校验结果

```
工作区干净（git status 空）
tag baseline-0.1.29 == HEAD d64fcb4
git diff --stat baseline-0.1.29  → 空（工作区与基线一致）
仓库内无 .apk / .aar
磁盘上 _lan/*.apk 与 app/libs/engine.aar 完好未受影响
```

### 后续约定

每次改完：改代码 → 更新基线说明对应章节 → 重建 AAR → 打包校验 → 复制到 `_lan/`
→ 更新 index.html 的 SHA256 → commit → `git tag -a baseline-<versionName>`。

tag 命名统一 `baseline-<versionName>`（不用 `v0.1.29`），一眼区分「能装能连的基线」
和普通版本号。

0.1.29 的技术改动（断流三级恢复 / 标准端口扫描 / 2 分钟预算）记在
`.workbuddy-ai/memory/2026-10-18.md` 末尾，这里不重复。
