# 2026-10-18

## 0.1.13：四个线上问题修复（原生核心 GOOL 无网 / AWG+赛风失败 / 赛风限速 / 首页延迟虚高）

### 根因与改动

1. **AWG + 赛风必失败**：`TherVpnService` 每次 `ACTION_START` 新起一条连接线程、共享 `engine`/`tun`，
   旧线程 120s 超时后 `teardown()` 把新会话的引擎关掉（日志特征：连接中途出现「停止核心进程 / 原生核心已停止」）。
   → 重写为 `Session` + `generation` 隔离，`live(s)` 守卫所有 Hub 写入，资源回收到会话自己的线程。
2. **psiphon 拨不出去（meek connection refused）**：`userNet.handleSocks` 在**物理网络**解析域名，拿到污染 IP。
   → `engine/usernet.go` 新增隧道内 DNS（`resolveInTunnel`/`buildDNSQuery`/`parseDNSAnswer`，跳过 CNAME、TTL 钳 60~600s、带缓存）。
3. **GOOL 连上但无网**：`persistent_keepalive=25s` > wireguard-go 的 15s「听不到回应」判定（10s+5s），空闲必然重握手，
   重握手在这条被 DPI 盯的线路上常失败。→ `engine.go`/`gool.go` 把 keepalive 钳到 ≤10s；`StatusJSON` 增加
   `hsAgeSec`/`outerHsAgeSec`/`tunnelRxBytes`/`tunnelTxBytes`；Kotlin 侧加断流看门狗（10s 采样，连续 3 次不涨判定断流，最多自动重连 2 次）。
4. **赛风只有 1~2Mbps**：gVisor 接收窗口小 + `TCPModerateReceiveBufferOption` 收缩 + `LimitTunnelProtocols` 里 meek/CDN 排太前。
   → `socks.go` 窗口 8/16MB、关 moderation、relay 256KB 池 + TCP_NODELAY；`AetherCore.TCP_ONLY_PSIPHON_PROTOCOLS` 把 meek/CDN 全部压到末尾。
5. **首页延迟几千 ms**：原来把一次完整 HTTP 探测的耗时写进 `latencyMs`。→ 新增 `net/Latency.kt`（TCP RTT，
   `direct` 穿隧道 / `throughSocks` 走本地 SOCKS5 CONNECT），`Hub.latency()` 是连接后唯一写入点；
   核心自报的 `exitInfo` 不再带延迟。

### 顺带修掉的隐患
- `NativeCore` 的 `pinnedIp`/`candidateEndpoints`/`excludeIps` 原是 companion 静态字段，并发连接互相覆盖 → 改实例字段。
- AWG + 赛风时 junk 参数没传给隧道（退化成普通 WG）→ `startWithPsiphon` 补 `junkCount/junkMinSize/junkMaxSize/junkI1`。
- 会话在启动过程中被 stop 会漏杀引擎/赛风进程（赛风会一直占 BoltDB 锁）→ 两个核心都加 `closing` + `ensureAlive()` 检查点。
- `engine.go` GOOL 分支补 `tunnelRxBytes`：带赛风时 `rxBytes` 会被 socks 转换层覆盖，用户空闲时冻住，看门狗会误判断流。

### 构建注意
- `build-engine.ps1` 直接 `powershell -File` 执行会因中文按 GBK 解码报「字符串缺少终止符」→ 改用内联命令：
  `gomobile bind -target android/arm64 -androidapi 26 -o app/libs/engine.aar .`（SDK=D:\Android\Sdk，NDK=27.0.12077973）。
- **增量打包会留下孤儿条目**：曾出现 APK 内多一份 4.2MB 的 `libgojni.so`（本地头文件名为空、不在中央目录），
  体积从 38.7MB 涨到 42.9MB。修法：`rm -rf app/build/outputs/apk app/build/intermediates/apk` 后重新 assembleDebug。
- 发布产物：`dist/ther-0.1.13-debug.apk`（38,701,725 字节），`dist/index.html` 已更新为 0.1.13，
  本机 `http://192.168.5.8:8080/` 静态服务常驻（端口 8080）。

## 0.1.24：原生核心的 WireGuard / AWG 按电脑版（E:/aether internal/wgtun）重新对齐

用户反馈 0.1.23「完全错误、无法连接」，要求只改原生 WG/AWG、其它不动。逐条比对电脑版后改四处：

1. **候选端点补回 seed**（`NativeCore.prepareEndpoints`）：电脑版 `buildCandidates(seed)` 的第一位
   永远是身份里登记的端点。0.1.23 只把 0xcf 探活结果当候选，探活全灭就直接返回空 → 上层报
   「所有端点都没完成握手（试了 0 个）」→ 无法连接。现在顺序是 seed → 新鲜探活 → 缓存，且
   **永不返回空**；探活为空时扫全池（电脑版 full sweep）；有缓存时不撒探针（电脑版热路径同样不扫）。
   顺带修掉一个隐患：`excludeIps` 现在包含 seed，否则用 seed 握手时加密包会绕回自己的 tun；
   只排除字面 IPv4（seed 解析失败会退回域名）。
2. **keepalive 改回 25s**（`engine/engine.go` Start）：电脑版 `buildUAPI` 写的就是
   `persistent_keepalive_interval=25`。0.1.13 把它钳到 10s 是错的推断——wireguard-go 的 15s
   判定是「发过数据但没收到已认证包」的被动保活，正常 keepalive 回包会重新计时。
3. **数据面自检加短重试**（`ExitInfo.probeDataPlaneSettled`）：照搬电脑版 `verifyDataPlane`——
   一次探测失败后每 300ms 重试、骑过 3s 收敛窗口。单次探测会把「刚握手、路由还没收敛」的
   好端点判死，六个候选逐个被否 = 无法连接。
4. **没试过端点就不记身份失败**（`TherVpnService`）：`attempt > 0` 才 `noteConnectResult(false)`，
   避免连不上时连续两次触发 WARP 身份轮换（反复注销/注册）。

对齐但无需改动的：UAPI 键顺序、`allowed_ip` 双栈、MTU 1280、AWG junk 默认 6/10/50、
不发 reserved 字节、`SwitchEndpoint` 只改 peer endpoint（同电脑版 setEndpoint）。

产物：`_lan/ther-0.1.24-arm64.apk`（38,719,697 字节，SHA256 073c8aa4…85ac），
`_lan/index.html` 已更新，本机 `http://192.168.5.8:8000/` 常驻。

## 0.1.25：原生核心 GOOL / 赛风出口（两条嵌套路径）

对照官方核心仓库（CluvexStudio/Aether，`aether/src/lib.rs` 的 `run_warp_in_warp` +
`spawn_udp_forwarder`）改的，关键发现：

- 官方 GOOL 建**外层**时 `obfuscate=true`、`keepalive=5`；内层 MTU 1200。我们之前是
  裸 WG 外层 + keepalive 10 + MTU 1420。`.tmp/gool3.log`（今日 14:14 实验）正好是反面证据：
  外层 0.9s 握手成功、数据面自检也过，之后 `userNet rx` 恒为 0、内层两次 initiation 零回包。
- 官方内层 peer 指向**本地 127.0.0.1 的 UDP 转发器**（`outer.open_udp()` 的源地址 = 外层身份 IP），
  我们的 `tunnelBind` 是等价的（直接在 outer netstack 里 DialUDP），这块不用改。
- 官方强制 `outer.ip() != inner.ip()`，并优先用 `:2408` 的 seed 地址。

改动（全部只碰嵌套路径）：
1. `goolOuterConfig`：keepalive 5（新常量 `GOOL_OUTER_KEEPALIVE`）、外层**无条件**带 AWG junk 6/10/50。
2. `startWithPsiphon` 的隧道：junk 不再只在选 AWG 时带，**总是带**（它是赛风的载体）。
3. `prepareEndpoints(protocol, nested)`：嵌套路径候选顺序改为「探活 → 缓存 → seed」，且永远重扫探针；
   普通 WG/AWG 仍是 seed 优先（0.1.24 的行为不变）。
4. GOOL 内层改为每次按当轮外层重算（`pickInnerEndpoint`）：优先跨 /24 + :2408。
5. `pickPort(avoid)`：隧道内 socks 与赛风监听不再可能拿到同一个端口（原来赛风 bind 失败会被
   `waitAnyPort` 误判成「已就绪」，白等 25s×2）。
6. GOOL 尝试上限 2 → 3。

注意：`原生核心连接修复说明.md` 第三节的旧结论「GOOL 内层不可能成功」是基于我们自己的实现
（外层裸 WG）得出的；官方实现能通，差别就在外层的混淆/keepalive。这次先按官方对齐，
若仍失败，下一步用真机日志确认内层是「零回包」还是「有回包但握手失败」。

## 0.1.27：端点全灭自动重扫再来一轮 + GOOL 内层落点「在隧道里」验活

用户给了新日志 `ther-1792336580121.log`，提两个设计问题：①GOOL 还是连不上，而且候选只有
3 个、3 个失败后不重连不换端点；②赛风路径也只剩 3 个端点，全失败就自动停止 —— 用户明确说

### 日志里挖到的 GOOL 真根因

`23:12:41~23:13:16` 两次 GOOL：外层 `188.114.97.99:7103` / `8.39.214.187:1002` 都在
0.3~0.6s 握手成功、`verifyDataPlane` 也过；内层落点 `8.39.214.187:1002`、
`8.39.214.201:3854`、`188.114.97.99:7103` 各 8s 零回包，`userNet rx` 从 112 一动不动，
只有 `tx` 在涨（内层 initiation 确实发出去了）。**这几个落点全是刚在手机上真握手通过的端点**
→ 结论：手机直连可达 ≠ 从外层 WARP 内部可达。旧逻辑用「手机上验过的」地址当内层落点，
所以外层永远好的、内层永远零回包。

### 改动

1. `engine/probe.go` 新增 `probeWarpThrough` / `probeWarpThroughPool`：从 `userNet`
   （外层隧道）里 `DialUDP` 发 0xcf 探针，并发扫、按隧道内 RTT 升序返回。
2. `engine/gool.go`：外层握手 + 数据面通过后，先用上面的探针扫 `innerCandidates`；
   有回包就只用回包的落点握手（最多 3 个）；全灭则 `innerStandardPool()` 再扫一遍
   （同批 IP 换 2408/500/1701/4500 + 每个 anycast 段 `.1:2408`，aether 官方 GOOL 内层
   就是 `188.114.96.1:2408`）；还是没有就按原顺序硬试并打 WARN（不判死，无回归）。
   新增 `goolInnerProbeWait=1.5s`、`goolInnerMaxLandings=3`、`capLandings`、`aliveAddrs`。
3. `TherVpnService.connect` 的 `!handshaken` 分支重写：不再 `throw`，改成
   `connectRounds++` → `NativeCore.invalidateCache()` → `newSession(auto=true)`。
   **必须换会话**：`prepareEndpoints` 只能在 `establish()` 之前跑（tun 一起来探针全进隧道），
   新会话线程会先 `reap(旧会话)` 关 tun 再扫。`MAX_CONNECT_ROUNDS=3`、
   `CONNECT_TOTAL_BUDGET_MS=300_000`；`connectRounds==0` 时在 connect() 开头重置
   `connectStartedAt`（断流自动重连也能用满额度）；连上后 `connectRounds=0`。
4. **自动重试的轮次不记身份失败**：`noteConnectResult(false)` 只在真正放弃时调一次，
   中间轮次只 `invalidateCache()`（新增 public 方法，只删 nodes-*.json）。否则一轮连接就把
   `failStreak` 顶到 2、下一次连接直接注销重注册 WARP 身份。
5. 上限：GOOL 每轮 2 → 3；`pickInnerCandidates` 默认 2 → 3。
6. `基线说明.md` 升到 0.1.27：新增 3.4 节（端点全灭的自动重扫）、红线 12~15、
   症状表 4 行、证伪表 2 行、日志样例、第 9 节排查步骤重写。

## 0.1.29（2026-10-19 凌晨）—— 断流三级恢复 + 标准端口扫描 + 2 分钟预算

输入日志：`ther-1792339366626.log`（0.1.28 首次连上，但中间自动断开重连 2 次）。
用户六点要求：少断开重连 / WG-AWG 是否也要改扫描 IP 段 / 加保活 /
首轮无端点不能直接失败要重试 / 总时间 ≤2 分钟 / 首连提速 + 端点质量。

### 根因（日志证据）
```
23:58:15.968 [Core] Retrying handshake because we stopped hearing back after 15 seconds
23:58:16.624 [Vpn]  隧道连续 12s 传不动数据，判定断流
23:58:16.626 [Vpn]  自动重连 1/2（重新扫描节点）
```
引擎 15s 时刚开始自愈重握手，我们 0.6s 后就把会话拆了 —— 亲手杀掉唯一能自愈的机会，
然后花 28s 重来一遍。这就是「自动断开重连好几次」。
另一处：gen=2 探活花了 **23.5s**，是小样本全灭后退回「扫全池 3810 个」造成的。

### 改动
1. **断流三级阶梯**（`TherVpnService.startHealthLoop`，按墙钟静默秒数判）：
   12s 只记日志 + 打「断流现场」→ 18s `NativeCore.recoverEndpoint()` 会话内换端点
   （设备不重建、不重扫）→ 36s 才 `newSession()`。静默计时不因换端点重置。
2. **给 wireguard-go 打补丁** `third_party/wireguard/device/force.go`：
   新增 `Device.ForceHandshake(pubHex)`。上游没有这个入口，只改 endpoint 的话设备
   会拿旧 keypair 往新地址发数据，对端静默丢弃，恢复要 20s。有它之后 1~2s。
   `Engine.SwitchEndpoint` 换完顺手调它。
3. **扫描改成标准端口优先 + 分级 + 8s 硬预算**（`engine/probe.go`）：
   `stdPorts = {2408,500,1701,4500}`，`standardPortAddr(i)` 纯函数映射（前 60 个是
   各段 .1×4 端口，之后 host×port×段 三维铺开、端口在最内层轮转），
   `ProbeEndpoints(timeout, limit, budgetMs)` 三级 240→960→高位端口 1200，
   `probePoolUntil` 带 deadline。**WG/AWG/GOOL 外层共用这一个入口，一起改了**。
4. **keepalive 上限 15s、实取 12s**（`engine.go` + `AppSettings.keepalive` 默认 25→12）。
   依据：wireguard-go「听不到回应」判定 = KeepaliveTimeout(10)+RekeyTimeout(5)=15s。
5. **2 分钟总预算**：`CONNECT_TOTAL_BUDGET_MS` 300s→120s、`MAX_CONNECT_ROUNDS` 3→4，
   端点循环里也卡同一个 deadline；连上时重置 `connectStartedAt`（原来会带着一小时前
   的起点去卡预算）。GOOL `goolInnerMaxLandings` 4→3（最坏 25s/端点 ×3 = 75s）。
6. **端点质量**：`badEndpoints`（30 分钟 TTL，只降序不删除）+ `reorderByHealth()`，
   断流时 `markEndpointBad(currentEndpoint())`。`armRecovery()` 把换端点游标移到
   当前端点之后（否则第一次断流会把连接阶段已失败的那个再试一遍）。
7. **可观测性**：`StatusJSON` 加 `outerRxBytes/outerTxBytes/endpoint`；
   启动失败时 `drainEngineLogs()` 把引擎环形缓冲倒出来（以前失败现场全丢）。

### 踩坑

  语法错误，改成 `cands`。
- `probeEndpoints` 从 2 参数变 3 参数后，`engine/cmd/gooltest/main.go` 也要改。
